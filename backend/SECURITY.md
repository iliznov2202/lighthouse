# Безопасность «Маяка»

Проверка и изменения: 1 октября 2026 года. Этот файл описывает реализованные меры и обязательные условия подключения реальных пользователей. Production-развертывание ещё не выполнено.

| Требование | Текущее состояние |
|---|---|
| Пароли только hash | Argon2id; публичная проекция пользователя не содержит hash |
| Refresh token только hash | SHA-256 для 48 случайных байт, одноразовая атомарная ротация, абсолютный срок сессии |
| HTTPS | Подготовлены Caddy и production Compose; приложение отклоняет HTTP в production. Публичный сертификат ещё не проверен |
| Rate limiting | Nest Throttler: 120 запросов/минуту на IP и handler; register/login — 10, refresh/logout — 30; 429 + Retry-After |
| Типы загружаемых файлов | Загрузок нет; multipart и другие не-JSON тела отклоняются с 415. Проверку содержимого файлов нужно реализовать при добавлении uploads |
| Размер файлов | Загрузок нет. Сейчас JSON ограничен 32 КБ на API и proxy; отдельные файловые лимиты обязательны при добавлении uploads |
| Секреты во frontend | В текущих исходниках frontend не найдены; серверные секреты только в ignored env и окружении deployment |
| CORS | Явный allowlist origins. Wildcard запрещён; production принимает только HTTPS origins и отклоняет localhost |
| Mass assignment | DTO + whitelist + forbidNonWhitelisted; Prisma получает явно перечисленные поля; userId берётся из проверенного JWT |
| Чужие ДЗ и посты | Этих модулей нет. Проверки владельца/школы/класса должны появиться вместе с ними, до публикации endpoints |
| Backup PostgreSQL | Скрипты custom-format backup и восстановления в отдельную пустую базу; локальный цикл backup/restore проверен. Production-расписание и внешнее хранение ещё не настроены |
| Dev / production базы | Разные Compose-проекты, volumes, env; production URL обязан использовать базу с суффиксом `_prod`, dev/test её отклоняет |
| Административный аудит | AuditModule и append-only AuditLog готовы; class create/join пишутся транзакционно. Административных endpoints ещё нет; их события потребуется подключить |

## Production и HTTPS

Скопировать `.env.production.example` в игнорируемую `.env.production`. Назначить новые production-секреты, реальные `API_DOMAIN` и `FRONTEND_ORIGINS`. Dev-секреты и пользователей seed не переносить. DNS домена API должен указывать на сервер, порты 80/443 — быть доступны Caddy. Сертификаты и автоматическое перенаправление HTTP на HTTPS обеспечивает [Caddy Automatic HTTPS](https://caddyserver.com/docs/automatic-https).

Использовать production-конфигурацию самостоятельно, не объединять её с dev Compose:

```sh
docker compose --env-file .env.production -f compose.production.yml build
docker compose --env-file .env.production -f compose.production.yml up -d postgres
docker compose --env-file .env.production -f compose.production.yml run --rm api npm run db:deploy
docker compose --env-file .env.production -f compose.production.yml up -d
```

Production API и PostgreSQL не публикуют порты наружу. Только Caddy доступен извне. Приложение доверяет ровно одному proxy hop (`TRUST_PROXY=1`); Caddy перезаписывает `X-Forwarded-For` и `X-Forwarded-Proto`, чтобы клиент не мог обойти лимиты поддельными заголовками. На одном хосте с API на loopback можно использовать `TRUST_PROXY=loopback`. Никогда не применять `trust proxy=true` или публиковать API напрямую с доверенным proxy. При добавлении CDN/LB схема доверия должна быть пересмотрена.

Helmet ставит защитные заголовки; HSTS включён только в production. Swagger там отключён. Между Caddy и API используется HTTP по внутренней Docker-сети; между удалёнными хостами требуется защищённый транспорт. Для внешнего PostgreSQL использовать проверку серверного TLS-сертификата и секреты провайдера. DB user приложения должен иметь только необходимые права, без superuser/DDL; миграции выполнять отдельной ролью. Текущий Compose — стартовая конфигурация, разделение PostgreSQL-ролей администратор должен выполнить перед публичным запуском.

Лимиты реализованы официальным [Nest Throttler](https://docs.nestjs.com/security/rate-limiting). Счётчики хранятся в памяти одного процесса и сбрасываются при рестарте. Перед несколькими репликами нужен общий storage (например Redis) или распределённый limiter на ingress. Разные endpoints имеют отдельные счётчики. Не использовать ограничения как единственную защиту от распределённого перебора; перед массовым запуском нужны наблюдение за неудачными входами и дополнительные правила на ingress.

## Резервное копирование

Скрипт использует [pg_dump custom format](https://www.postgresql.org/docs/17/app-pgdump.html); пароль передаётся дочернему процессу через `PGPASSWORD`, а не command line. Нужны pg_dump/pg_restore той же основной версии, что сервер, или новее. В production image установлены клиенты PostgreSQL 17. Для локального сервера можно задать `PG_DUMP_PATH` / `PG_RESTORE_PATH`.

```sh
npm run db:backup
```

Архив сохраняется в ignored `backups/` (или `BACKUP_DIR`). Он содержит персональные данные и hash: это не шифрование. На Unix директория создаётся с 0700, архив — с 0600; в Windows доступ ограничить ACL. До запуска production создать host-директорию `backups` для UID 1000 (пользователь node контейнера) и ограничить доступ.

Создание production backup:

```sh
sh deploy/backup-production.sh
```

Шаблон строки cron на сервере, например ежедневный запуск в 02:00 по времени сервера:

```cron
0 2 * * * /bin/sh /srv/mayak/backend/deploy/backup-production.sh
```

Расписание не установлено автоматически. До реальных пользователей назначить ответственного, целевые RPO/RTO, мониторинг успешности, политику хранения (например 7 ежедневных, 4 еженедельных, 6 ежемесячных) и зашифрованную внешнюю копию с отдельными ключами и доступом. Не считать Docker volume backup. Регулярно проверять восстановление; для меньшего RPO предусмотреть PITR/WAL средствами PostgreSQL или провайдера.

Восстановление только в отдельно созданную пустую базу:

```sh
# Перед командой задать RESTORE_DATABASE_URL в окружении/секретах.
npm run db:restore -- backups/mayak-TIMESTAMP.dump
```

Скрипт запрещает исходную базу, базу с суффиксом `_prod` и непустую базу, не выполняет drop/clean; restore проходит одной транзакцией. После восстановления проверить миграции, количество/содержимое сущностей и запуск API на отдельной конфигурации. Переключение production на восстановленную базу — отдельная управляемая операция.

## Будущие uploads, homework, feed, moderation

При добавлении uploads обязательны серверная проверка сигнатуры содержимого и разрешённых форматов (первоначально JPEG/PNG/WebP), согласованность MIME и расширения, ограничение байт, количества файлов, размеров/пикселей изображения и общего объёма пользователя. Заявленному клиентом MIME доверять нельзя. SVG/HTML и исполняемые файлы не принимать. Ограничивать входной поток до буферизации, генерировать имя на сервере, проверять владельца и доступ на чтение/удаление. Хранилище — вне исполняемого web root, без публичного листинга; при загрузке документов понадобится антивирусная проверка. Текущий JSON-лимит нельзя считать проверкой файлов.

При добавлении ДЗ/постов каждое изменение и удаление должно проверять `authorId === authenticatedUser.id`, школу, класс и статус ресурса на сервере. Проверка в той же транзакции или условном запросе с `id + authorId + schoolId/classId`; клиентские authorId/ownerId/role отклонять. Модераторские исключения — отдельная проверяемая политика, с обязательным аудитом. Тесты должны включать попытки пользователя B изменить/удалить ресурс пользователя A, получить ресурс чужого класса/школы и подменить владельца в body.

В AuditLog хранить идентификатор проверенного актёра, фиксированное действие, тип/идентификатор объекта и время. AuditService вызывается в транзакции вместе с изменением. Триггер блокирует UPDATE/DELETE/TRUNCATE; суперпользователь базы способен снять эту защиту, поэтому runtime-роль не должна владеть таблицей/триггером. Лог не содержит email, пароли, токены, свободный текст или полный HTTP-body, не имеет публичного API. Повторное вступление не создаёт повторную запись, неуспешные бизнес-операции не оставляют успешное событие. Модерацию, блокировки, смену прав и другие административные команды подключать к аудиту при реализации. Для аудита нужен отдельный доступ на просмотр, срок хранения и защищённый внешний экспорт.

Frontend может содержать только публичный URL API. Значения `VITE_*` становятся доступными браузеру; API keys, JWT secret, database URLs и service credentials туда не помещать. Access token предпочтительно хранить в памяти; решение для refresh token на frontend пока не реализовано. При переходе на HttpOnly cookies добавить CSRF-защиту, Secure/SameSite и согласованную CORS-политику.

## Проверки

```sh
npm run build
npm run prisma:validate
npm run db:deploy
npm run test:security
# Для test:e2e запустить API и seed на локальной dev-базе.
npm run test:e2e
npm audit
```

`test:security` проверяет production validation, запрет HTTP, доверие HTTPS proxy, HSTS, закрытый Swagger, заголовки, 413/415, malformed JSON, mass assignment, 429 и подделку X-Forwarded-For. `test:e2e` также проверяет hash токенов/паролей, конкурентные операции, доступ между школами, транзакционный и неизменяемый аудит. Интеграционные тесты сохраняют audit-события тестовых действий; тестовых пользователей и классы удаляют. Для обеих проверок нужна отдельная dev-база; запуск на production запрещён конфигурацией.

Фактически проверено локально: сборка и Prisma validate, две применённые миграции, REST e2e, три security-теста, создание custom-format backup и восстановление в отдельную временную базу (совпали счётчики всех таблиц и сохранён audit trigger), `npm audit` — 0 уязвимостей. Использованы PostgreSQL 18.4 и клиенты 18.6. Docker на машине отсутствует: сборка production image, запуск Compose/Caddy, публичный TLS-сертификат и production backup-расписание не проверены. YAML-конфигурации проходят синтаксический разбор.
